# Runbook 2026-11-08: Dograh 1.51.0, caller memory, record lookup, call outcomes

The owner runs this in a terminal (not the `!` box: several steps are interactive). Nothing here was run by the agent that wrote it;
every step marked **[unverified offline]** depends on the live Railway project, Dograh or Synchronize and could not be checked
without them. Secrets are typed only at silent reads (`IFS= read -rs`), never as arguments, and are unset at the end. What changed
and why: `UPGRADE-1.51.md` and `workflows/README.md` (Caller memory, Live wiring, Evals). A line that says `STOP` means stop there;
a line that says `go to R` means stop and roll back from the "Where to enter" table in R.

Order that matters:

- Steps 1–4 (Dograh 1.51.0) do not depend on Synchronize and can run first. Run steps 2–3 when no call is expected: if Railway keeps
  the 1.49 api serving while the new one migrates, an English call in that minute ends without its spoken goodbye (`UPGRADE-1.51.md`,
  Behaviour callers notice; not verifiable offline).
- Step 5 (go-live) needs the Synchronize release with the caller-work route and the pre-call caller fields (branch
  `fm/261108_voice_caller_context`) deployed and healthy: the probe refuses to continue without `/api/voice/tools/caller-work`. It posts the
  run id as a JSON integer, as the lookup tool's body template does, but Synchronize answers a body it refuses like an unknown run, so only
  test call 2 (step 8) shows the integer is accepted.
- Step 5 needs `$FORK` clean at the reviewed commit or a later one that contains it (`golive.py` reads the templates from `HEAD`).
- Step 6 (evals) needs only step 5. Step 7 routes the Korean number only after step 6's results are read, so the first real call reaches
  the wired workflow and nobody hears the new Korean prompts before they were measured.

## 1. Voice Postgres backup **[unverified offline]**

```bash

#     base64 keeps the custom-format dump byte-exact through the SSH stream; pipefail reports a local break in the stream.
DUMP="$DUMP_DIR/dograh-pre-151-$(date -u +%Y%m%dT%H%M%SZ).dump"
( set -o pipefail; railway ssh --service "$PG_SERVICE" -- sh -c 'pg_dump -U "${POSTGRES_USER:-postgres}" -d "${POSTGRES_DB:-postgres}" -Fc | base64' | tr -d '\r' | base64 -d > "$DUMP" ) && chmod 600 "$DUMP" && ls -l "$DUMP" || echo 'STOP: the dump stream failed'

#     (including a pg_dump that failed inside the container) fails here.
docker run --rm -v "$DUMP_DIR:/b:ro" postgres:17 pg_restore -f /dev/null "/b/$(basename "$DUMP")" && echo "dump reads end to end" || echo 'STOP: the dump is incomplete'
# 1e. Extra check: the tables Dograh needs are in it.
docker run --rm -v "$DUMP_DIR:/b:ro" postgres:17 pg_restore -l "/b/$(basename "$DUMP")" | grep -cE 'TABLE public (alembic_version|tools|workflows|workflow_runs|workflow_definitions) '   # expect 5
```

when R3 printed `b3c1d9e4f7a2`; after any other R3 failure skip R4 and go to R5 (the 1.49.0 image cannot start on the 1.51 schema).

**R4. Images back, api first.** Only after R3 printed `b3c1d9e4f7a2`, or `schema_version` printed it (row "Steps 2–4").

```bash
railway service source connect --image dograhai/dograh-api:1.49.0 --service dograh-api --environment production
railway service status --service dograh-api --environment production   # until SUCCESS
curl -fsS --max-time 20 "$DOGRAH_PROOF_BASE_URL/api/v1/health" && echo " api healthy"   # if this does not print, stop here and go to R5
railway service source connect --image dograhai/dograh-ui:1.49.0 --service dograh-ui --environment production
railway service status --service dograh-ui --environment production    # until SUCCESS
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 20 "$DOGRAH_UI_URL/auth/login"   # expect 200 (1.49 has the same public login page)
```

If the UI deployment does not reach SUCCESS or the check does not print 200, the api is already back on 1.49.0 and serving calls: redeploy the UI
(`railway service redeploy --service dograh-ui --environment production --from-source --yes`) and repeat the two UI checks; do not open Tools
until it prints 200.

**R5. Last resort: restore the step-1 dump.** Only when R3 failed for a reason R2 cannot fix, R4's api health check failed, or the 1.51 api does
not run (row "Steps 2–4"). Every call after the backup is lost. The api stops first, before any image change, so nothing writes.

```bash
railway down --service dograh-api --environment production --yes
railway connect "$PG_SERVICE" --tunnel-only -P 55432          # second terminal; leave it open
IFS= read -rs PGPASSWORD; export PGPASSWORD; printf '\n'
docker run --rm -e PGPASSWORD -v "$DUMP_DIR:/b:ro" postgres:17 pg_restore -h host.docker.internal -p 55432 -U "$PG_USER" -d "$PG_DB" --clean --if-exists --no-owner "/b/$(basename "$DUMP")"
schema_version   # expect b3c1d9e4f7a2
railway service source connect --image dograhai/dograh-api:1.49.0 --service dograh-api --environment production
railway service redeploy --service dograh-api --environment production --from-source --yes
railway service status --service dograh-api --environment production   # until SUCCESS
curl -fsS --max-time 20 "$DOGRAH_PROOF_BASE_URL/api/v1/health" && echo " api healthy"
railway service source connect --image dograhai/dograh-ui:1.49.0 --service dograh-ui --environment production
railway service status --service dograh-ui --environment production    # until SUCCESS
curl -fsS -o /dev/null -w '%{http_code}\n' --max-time 20 "$DOGRAH_UI_URL/auth/login"   # expect 200
unset PGPASSWORD
```

After R1 the lookup tools stay in the organization unreferenced, like the credential; after R4 the End Call goodbyes are back in the 1.49 fields
(the downgrade converts one start message back).
